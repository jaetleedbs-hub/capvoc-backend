## 현재 상황 분석

### 1. 기존 인프라
- ✅ **Jasypt 암호화 라이브러리** 이미 구축됨
  - `CryptoUtil`: Spring Context 기반 암호화/복호화 유틸리티
  - `EncryptionTool`: 독립 실행 가능한 암호화 도구
  - `JasyptConfig`: PBEWITHHMACSHA512ANDAES_256 알고리즘 사용
- ✅ **마스킹 기능** 이미 구현됨 (`masking` 패키지)
- ✅ **JPA 기반** 엔티티 관리 (Spring Data JPA)

## 암호화 구현 방안

### 방안 1: JPA AttributeConverter 기반 (권장) ⭐

#### 개요
JPA의 `@Convert` 어노테이션을 사용하여 엔티티 필드 레벨에서 자동 암호화/복호화

#### 장점
- ✅ **투명한 암호화**: Service 레이어 코드 변경 최소화
- ✅ **자동 처리**: 저장 시 암호화, 조회 시 복호화 자동 수행
- ✅ **유지보수 용이**: 암호화 로직이 한 곳에 집중
- ✅ **성능 최적화 가능**: Converter 인스턴스 재사용

#### 단점
- ⚠️ **검색 제약**: 암호화된 필드로는 LIKE 검색 불가
- ⚠️ **인덱스 제약**: 암호화된 필드 인덱스 효율성 저하
- ⚠️ **마이그레이션 필요**: 기존 데이터 암호화 마이그레이션 필요

#### 구현 예시

```java
// 1. 암호화 Converter 생성
@Converter
public class EncryptedStringConverter implements AttributeConverter<String, String> {
    private static CryptoUtil cryptoUtil;
    
    @PostConstruct
    public void init() {
        // Spring Context에서 CryptoUtil 주입
    }
    
    @Override
    public String convertToDatabaseColumn(String attribute) {
        if (attribute == null) return null;
        return CryptoUtil.encryptStatic(attribute);
    }
    
    @Override
    public String convertToEntityAttribute(String dbData) {
        if (dbData == null) return null;
        return CryptoUtil.decryptStatic(dbData);
    }
}

// 2. 엔티티에 적용
@Entity
@Table(name = "cmpt_user")
public class CmptUserEntity {
    @Column(name = "mbl_tel_no", length = 11)
    @Convert(converter = EncryptedStringConverter.class)
    private String mblTelNo;
    
    @Column(name = "eml_addr", length = 40)
    @Convert(converter = EncryptedStringConverter.class)
    private String emlAddr;
}
```

#### 변경 영향도
- **엔티티**: 각 필드에 `@Convert` 추가 (낮음)
- **Service**: 변경 없음 (낮음)
- **Repository**: 변경 없음 (낮음)
- **Mapper (MyBatis)**: 직접 쿼리 사용 시 수동 복호화 필요 (중간)

### 방안 2: Service 레이어에서 수동 암호화/복호화

#### 개요
Service 메서드에서 저장 전 암호화, 조회 후 복호화를 명시적으로 수행

#### 장점
- ✅ **유연성**: 필드별 선택적 암호화 가능
- ✅ **검색 가능**: 필요 시 평문으로 검색 후 암호화 저장
- ✅ **디버깅 용이**: 암호화/복호화 시점 명확

#### 단점
- ⚠️ **코드 중복**: 모든 Service 메서드에 암호화/복호화 로직 추가 필요
- ⚠️ **실수 가능성**: 암호화/복호화 누락 위험
- ⚠️ **유지보수 부담**: 암호화 로직 변경 시 모든 Service 수정 필요

#### 구현 예시

```java
@Service
@Transactional
public class CNS1010Service {
    private final CryptoUtil cryptoUtil;
    
    public void saveUser(CmptUserEntity user) {
        // 저장 전 암호화
        if (user.getMblTelNo() != null) {
            user.setMblTelNo(cryptoUtil.encrypt(user.getMblTelNo()));
        }
        if (user.getEmlAddr() != null) {
            user.setEmlAddr(cryptoUtil.encrypt(user.getEmlAddr()));
        }
        
        userRepository.save(user);
    }
    
    @Transactional(readOnly = true)
    public CmptUserEntity getUser(String userId) {
        CmptUserEntity user = userRepository.findById(userId).orElse(null);
        if (user != null) {
            // 조회 후 복호화
            if (user.getMblTelNo() != null) {
                user.setMblTelNo(cryptoUtil.decrypt(user.getMblTelNo()));
            }
            if (user.getEmlAddr() != null) {
                user.setEmlAddr(cryptoUtil.decrypt(user.getEmlAddr()));
            }
        }
        return user;
    }
}
```

#### 변경 영향도
- **엔티티**: 변경 없음 (낮음)
- **Service**: 모든 CRUD 메서드 수정 필요 (높음)
- **Repository**: 변경 없음 (낮음)
- **Mapper (MyBatis)**: 조회 결과 수동 복호화 필요 (중간)

### 방안 3: AOP 기반 자동 암호화/복호화

#### 개요
AOP를 사용하여 Repository 메서드 호출 전후에 자동 암호화/복호화 수행

#### 장점
- ✅ **코드 변경 최소화**: Service 레이어 변경 없음
- ✅ **중앙 집중 관리**: 암호화 로직 한 곳에서 관리
- ✅ **유연한 적용**: 어노테이션 기반 선택적 적용 가능

#### 단점
- ⚠️ **복잡도 증가**: AOP 설정 및 디버깅 어려움
- ⚠️ **성능 오버헤드**: AOP 프록시 생성 비용
- ⚠️ **예외 처리 복잡**: 암호화 실패 시 예외 처리 복잡

#### 구현 예시

```java
@Aspect
@Component
public class EncryptionAspect {
    private final CryptoUtil cryptoUtil;
    
    @Around("@annotation(Encrypt)")
    public Object encrypt(ProceedingJoinPoint joinPoint) throws Throwable {
        Object[] args = joinPoint.getArgs();
        // 인자 암호화 처리
        for (Object arg : args) {
            if (arg instanceof CmptUserEntity) {
                encryptEntity((CmptUserEntity) arg);
            }
        }
        return joinPoint.proceed(args);
    }
    
    @AfterReturning("@annotation(Decrypt)", returning = "result")
    public void decrypt(Object result) {
        // 결과 복호화 처리
        if (result instanceof CmptUserEntity) {
            decryptEntity((CmptUserEntity) result);
        }
    }
}
```

#### 변경 영향도
- **엔티티**: 변경 없음 (낮음)
- **Service**: 변경 없음 (낮음)
- **Repository**: 어노테이션 추가 (낮음)
- **AOP 설정**: 새로운 Aspect 클래스 추가 (중간)

## 최적화 방안

### 1. 성능 최적화

#### 1.1 Converter 인스턴스 재사용
```java
@Component
public class EncryptedStringConverter implements AttributeConverter<String, String> {
    private static final ThreadLocal<CryptoUtil> cryptoUtilCache = new ThreadLocal<>();
    
    // Converter 인스턴스 재사용으로 초기화 비용 절감
}
```

#### 1.2 암호화 풀링
- `JasyptConfig`에서 이미 `PooledPBEStringEncryptor` 사용 중
- `poolSize` 조정으로 동시 처리 성능 향상 가능

#### 1.3 배치 처리 최적화
```java
// 대량 조회 시 배치 복호화
@Transactional(readOnly = true)
public List<CmptUserEntity> getUsers(List<String> userIds) {
    List<CmptUserEntity> users = userRepository.findAllById(userIds);
    // 배치 복호화로 성능 향상
    users.forEach(this::decryptEntity);
    return users;
}
```

#### 1.4 캐싱 전략
- 자주 조회되는 사용자 정보는 복호화 후 캐싱
- Spring Cache (`@Cacheable`) 활용

### 2. 검색 최적화

#### 2.1 검색용 해시 필드 추가
```java
@Entity
public class CmptUserEntity {
    @Column(name = "mbl_tel_no", length = 11)
    @Convert(converter = EncryptedStringConverter.class)
    private String mblTelNo;
    
    // 검색용 해시 필드 (SHA-256)
    @Column(name = "mbl_tel_no_hash", length = 64)
    @Index(name = "idx_mbl_tel_no_hash")
    private String mblTelNoHash;
}
```

#### 2.2 부분 검색 대응
- 전화번호 뒷자리 4자리 별도 컬럼 저장 (검색용)
- 이름 초성 검색용 필드 추가

### 3. 데이터베이스 최적화

#### 3.1 컬럼 크기 조정
- 암호화 후 데이터 크기 증가 (약 1.5~2배)
- VARCHAR 길이 여유 확보 필요

#### 3.2 인덱스 전략
- 암호화된 필드는 인덱스 효율성 저하
- 검색용 해시 필드에 인덱스 생성

### 4. 마이그레이션 최적화

#### 4.1 점진적 마이그레이션
```sql
-- 1단계: 암호화 컬럼 추가
ALTER TABLE cmpt_user ADD COLUMN mbl_tel_no_encrypted VARCHAR(255);

-- 2단계: 배치로 기존 데이터 암호화
UPDATE cmpt_user SET mbl_tel_no_encrypted = ENCRYPT(mbl_tel_no) 
WHERE mbl_tel_no_encrypted IS NULL;

-- 3단계: 애플리케이션 코드 배포

-- 4단계: 기존 컬럼 삭제
ALTER TABLE cmpt_user DROP COLUMN mbl_tel_no;
ALTER TABLE cmpt_user RENAME COLUMN mbl_tel_no_encrypted TO mbl_tel_no;
```

#### 4.2 배치 마이그레이션 스크립트
- 대용량 데이터는 배치로 나누어 처리
- 트랜잭션 단위 조정으로 롤백 위험 최소화

## 권장 사항

### 1. 구현 방안 선택

**권장: 방안 1 (JPA AttributeConverter)**

이유:
- ✅ 코드 변경 범위 최소
- ✅ 유지보수 용이
- ✅ Service 레이어 투명성 유지
- ✅ 롤백 용이

### 2. 단계별 구현 계획

#### Phase 1: 인프라 구축 (1주)
1. `EncryptedStringConverter` 구현
2. 테스트 코드 작성
3. 성능 테스트 수행

#### Phase 2: 핵심 엔티티 적용 (2주)
1. `CmptUserEntity` 적용
2. `CnslDscsnHstryEntity` 적용
3. 통합 테스트

#### Phase 3: 전체 엔티티 적용 (2주)
1. 나머지 엔티티 순차 적용
2. MyBatis Mapper 수정
3. 전체 통합 테스트

#### Phase 4: 데이터 마이그레이션 (1주)
1. 기존 데이터 암호화 스크립트 작성
2. 배치 마이그레이션 실행
3. 검증 및 모니터링

### 3. 주의사항

#### 3.1 암호화 키 관리
- ✅ 운영 환경에서는 반드시 환경변수 사용
- ✅ 키는 별도 키 관리 시스템에서 관리
- ✅ 키 로테이션 계획 수립

#### 3.2 검색 기능
- ⚠️ 암호화된 필드로는 LIKE 검색 불가
- ✅ 검색이 필요한 필드는 해시 필드 추가 고려

- API 응답 시 마스킹 기능과 연계하여 이중 보안
